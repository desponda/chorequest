Proposed Coin Audit Log Schema

Add a coin_transactions table to power the audit history you want:

CREATE TABLE coin_transactions (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  kid_id       uuid REFERENCES kids(id),
  family_id    uuid REFERENCES families(id),
  amount       integer NOT NULL,       -- positive = credit, negative = debit
  kind         text NOT NULL,          -- 'quest_approved' | 'reward_approved' | 'reward_denied'
                                       -- | 'reward_cancelled' | 'quest_rejected' | 'curse'
  reference_id uuid,                   -- quest completion or redemption id
  balance_after integer NOT NULL,      -- kid.coins after this transaction
  created_at   timestamptz DEFAULT now()
);

Every approval triggers an INSERT here. The UI reads this table to show each kid's full coin history.

CRITICAL Bug #1 — Double Deduction on Undo + Re-Approve
use-parent-actions.ts · fulfillRedemption() + undoRedemption()
When a parent approves a redemption, then undoes it, the redemption goes back to pending and re-appears in the approval queue. If the parent approves it again, coins are deducted a second time. Kid loses 100 coins for a 50-coin reward. This is the bug you reported.
Track a fulfilled_at timestamp on the redemption. Before deducting coins in fulfillRedemption(), check that fulfilled_at IS NULL. If already fulfilled, refuse and show a toast. Alternatively, don't allow undoing an approval — instead add a "deny after approval" flow that refunds coins with an explicit audit entry.
CRITICAL Bug #2 — Stale Coin Read on Approval
use-parent-actions.ts · fulfillRedemption() line ~255
kid.coins is read from in-memory component state (loaded at page open), not from a fresh DB fetch. If another approval happened since the parent opened the dashboard, this parent approves with the wrong balance, and the atomic deduction produces an incorrect final value.
Change the coin deduction to an atomic SQL operation: UPDATE kids SET coins = GREATEST(0, coins - {cost}) WHERE id = {id}. This is safe regardless of concurrent updates because it operates on the current DB value, not a cached one.
HIGH Bug #3 — No Server-Side Coin Guard on Request
api/kid/[id]/redeem/route.ts · POST handler
When a kid submits a redemption, the server checks available coins at that moment. But coins are not immediately deducted server-side. If a kid submits multiple requests in rapid succession before any pendingTotal is counted, all requests are accepted, potentially totalling more than the kid's balance.
Use a DB transaction: SELECT coins FROM kids WHERE id=? FOR UPDATE, sum existing pending costs, verify coins - pendingTotal >= newCost, then INSERT the redemption — all in one atomic operation.
HIGH Bug #4 — Denial Deletes Row, No Audit Trail
use-parent-actions.ts · denyRedemption()
When a parent denies a redemption, the row is hard-deleted. The kid's request silently disappears with no explanation. The parent also loses the record — they can't see what they denied. No history exists.
Change to soft-delete: UPDATE redemptions SET status='denied', denied_at=NOW() WHERE id=?. Show denied redemptions in history for both kid and parent, greyed out with a "✗ denied" label.
MEDIUM Bug #5 — No Kid Notification of Approval
api/kid/[id]/data/route.ts · redemptions fetch
The kid data endpoint only fetches status='pending' redemptions. When a parent approves, the item disappears from the kid's list without any notification. Kid sees their request vanish silently and doesn't know it was approved unless they notice coins decreased.
Fetch both 'pending' and recent 'approved' redemptions (last 7 days). Show approved ones as completed with a "✓ approved" badge. The existing toast on the kid page only fires when the kid's app is open during the approval — silent otherwise.
